## phux keys in brief
- A key is zero or more modifiers and one key, joined with `-`: `C-a`, `M-Enter`,
  `C-S-x`. `C-` is Ctrl, `M-` is Alt (`A-` means the same), `S-` is Shift. The letters
  are uppercase: `Ctrl-a` and `ctrl+a` are not phux keys.
- phux has no Cmd (Super) modifier. A source binding that uses cmd, super or command
  gets no line and goes under "Could not migrate".
- Named keys, case-sensitive: Tab, BackTab, Enter, Esc, Space, Backspace, Delete,
  Insert, Up, Down, Left, Right, Home, End, PageUp, PageDown, F1 to F24. Any other key
  is one letter, digit or ASCII punctuation character.
- A key names the physical key on a US layout: a capital letter means Shift (`"X"` is
  `"S-x"`), `"|"` is `"S-\\"` and `"?"` is `"S-/"`. Two spellings of the same key in
  one file are an error.
- Bindings live in tables. `[keybindings.prefix-table]` fires after the prefix
  (`[keybindings] prefix`, {{prefix}} by default). `[keybindings.global]` fires on its
  own and takes the key away from every program in every pane, so use it only where a
  line below says so. `[keybindings.modes.<name>]` fires while that mode is on.
- A value is an action name or an inline table with the action and its arguments:
  `"v" = { action = "split-pane", direction = "vertical" }`. `"x" = "none"` removes a
  binding, a phux default included.
- Keys pressed one after another are one string with spaces: `"t s"` in the prefix
  table is the prefix, then t, then s. A key either runs an action or starts a
  sequence, never both.
- Quote every key: `"|" = ...`, `'"' = ...`, `"\\" = ...`.
- Bind only the actions under "Actions you may bind" at the end of this prompt.

## Rules
- Never bind a macOS system shortcut: cmd+q, cmd+h, cmd+m, cmd+tab, cmd+space,
  cmd+shift+3, cmd+shift+4, cmd+shift+5 and ctrl+cmd+q. A source line on one of them,
  whatever it does, gets no line and goes under "Could not migrate" with the reason
  "macOS uses this key itself". Check every key in any modifier order (`shift+cmd+5` is
  cmd+shift+5), after expanding a source's own names for modifiers or a leader key.
- Where a source binding has no phux action, do not approximate it with a different
  one. Leave it out and report it.
- Merge, never replace: keep every line already in the target file. A line there
  changes only when a source line wins a conflict you asked me about.
- Write each key once per table. Never write two lines that leave the later to win.
- Never decide a conflict yourself. When the lines below say to ask, ask me and wait.

terminal's environment, and a bare `phux` could be a different phux.
1. Run `{{phux}} config check {{config_q}}`. It must exit 0 and print no problems. Fix the

2. Compare the file with the tables above, line by line: every line marked "write" is

3. Run `{{phux}} config reload` once. Do not ask me first: I asked for this migration, and
   nothing takes effect until the reload. If it fails with "operation not permitted" or
   cannot connect, your sandbox blocked it: do not retry it and do not work around it.
   If you can ask me to approve running one command outside your sandbox, ask once and
   run it again on approval. Otherwise tell me in one line: "Your sandbox blocked the
   reload; run `phux config reload` yourself." In the report, the reload is pending,
   not failed.
4. Run `{{phux}} config keys --json`. Its `skipped` list must be empty: each entry is a
   binding phux will not use. Fix the file, run steps 1 and 3 again, and repeat until it
   is empty.

## Report
Keep it short. Do not print the file, a diff, or command output. Give the path of the
file, then these five lists in this order, one line per entry, then one line each for
config check, reload and keys.
- Migrated: each source line written, quoted with its file and line number, the phux
  key it became and its action. A line marked "already phux's default" goes here with
  "(phux default)".
- Replaced phux defaults: one line per default a written line replaced, in words: what
  the key did before, what it does now, and the source line that won.
- Conflicts between sources: each key more than one source bound, which source won (by
  my answer), and the losing line quoted with its file and line number.
- Nothing to do: the lines marked "nothing to do". Group them by reason: one line per
  reason, naming the lines by file and line numbers.
- Could not migrate: every other source line, quoted as written with its file and line
  number, and one sentence on why (the table's reason, where it gives one). These are
  the lines I have to act on: each goes on its own line, never summarised together.
Never drop a line silently: every line in the tables above appears in exactly one list.
