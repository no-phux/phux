# L2 — Organization

**TL;DR.** The normative organization model: sessions, resource
membership, session lifetime, the Inbox, arrangements, revisions, and the
rules every organization command enforces. The commands themselves are
typed L1 `COMMAND`-envelope variants behind the `ORGANIZATION` feature;
there is no L2 frame family, and the L2 layer bit stays reserved. A
client that lacks the feature uses the legacy translation in L3.

---

## 1. Status and scope

Organization is server-owned state, not client convention
([ADR-0160](../adr/0160-sessions-own-resources-and-window-is-retired.md),
[ADR-0161](../adr/0161-organization-is-typed-commands-behind-a-feature-bit.md)).
This document owns what the organization records are and the rules
commands over them SHALL follow. Command, result, and event byte layouts
are owned by [L1.md](./L1.md) §5.7 and §7; the feature bit is owned by
[proto.md](./proto.md) §6.2; the scope verbs each command requires are
owned by [workload-auth.md](./workload-auth.md) §5 and §6.

The L2 discriminant range and the `HELLO.layers` bit `0x02` remain
reserved and unmounted. Organization is negotiated by
`ServerFeatureExt::ORGANIZATION`, not by a layer: its commands ride the L1
`COMMAND` envelope and its events ride the L1 event journal. An earlier
draft of this document specified a `CREATE_COLLECTION` /
`KILL_COLLECTION` service with Collection identities; that design is
withdrawn in full, and nothing here reuses its names or tags.

## 2. Records

### 2.1 Identifiers

A record has a **key**: 16 random bytes, minted when the record is
created, never reused, and never changed by rename or move. Keys exist for
the authority, sessions, resources, arrangements, and workspaces. A live
`SessionId` or `ResourceId` is a **handle**: valid for one server
instance, scoped by its `ServerInstance` token, and never written to the
organization store. `GetOrganization` reports both so a client can map one
to the other. Keys SHALL NOT appear in terminal I/O frames.

A reference across servers prefixes the authority key: `(AuthorityId,
SessionKey)`, and likewise for resources and workspaces. The text form is
lowercase base32 of the 16 bytes, displayed as the shortest unique prefix
of at least 6 characters and always accepted in full.

`Revision` is a `u64` per record that increases on every committed change
to that record. `ActivationId` is a `u64` per resource that increases from
1 with each execution. `OperationId` is 16 bytes drawn by the caller.

### 2.2 Session

A session has a key, a name, a lifetime, an intake mark, an ordered member
list, an optional arrangement, descriptive attributes, and a revision.

- **Name.** UTF-8, at most 256 bytes, unique among live sessions on the
  authority. Renaming changes the label only.
- **Lifetime.** `Persistent` or `Ephemeral` (§3).
- **Members.** Resource keys in creation order. Presentation order belongs
  to the arrangement.
- **Attributes.** Project, directory, and host label. They describe the
  session and never imply a level of organization above it.
- **Intake mark.** `awaiting_organization`, set on sessions imported by a
  migration (§4).

### 2.3 Resource membership

Every resource SHALL be a member of exactly one session on its authority.
A resource record carries its session key, its kind, an optional name, its
provenance (the actor that created it and any opener or parent), its
launch specification, its exit policy (§3.2), and its current or most
recent activation. Moving a resource between sessions changes membership
only; it SHALL NOT restart, signal, or re-key the resource. There is no
move between authorities.

### 2.4 Arrangement

An arrangement is a list of groups. A group has a 16-byte id, an optional
name, and one binary split tree whose leaves are entries. An entry has a
16-byte id and names a resource by key. Group and entry ids are random and
minted by whoever creates them.

A session's arrangement SHALL reference only that session's members, SHALL
NOT repeat an entry id, and SHALL carry split ratios in `(0, 1)`. An
encoded arrangement is at most 64 KiB. An entry never authorizes access to
the resource it names. When a resource is removed, its entries are dropped
in the same transaction.

Focus, selection, scroll, zoom, and native window geometry are never part
of an arrangement.

### 2.5 Activation

An activation records its id, the server instance that started it, its
state, start and end times, and its outcome. States are `Starting`,
`Running`, `Stopping`, `Completed`, `Failed`, `Lost`, and `Abandoned`. An
outcome is an exit status, a signal, a kind-specific result, or
`Unobserved`. A resource has at most one current activation unless its
kind says otherwise.

`Lost` means the server no longer holds a handle to an execution that may
still be running. A `Lost` resource SHALL refuse remove and relaunch with
`ExecutionUncertain` until it is terminated, or until a later startup finds
the process gone.

## 3. Lifetime and exit

### 3.1 Session lifetime

A `Persistent` session survives having no members and is removed only by
`SessionDelete`. An `Ephemeral` session SHALL be deleted in the same
transaction that removes its last member, and SHALL NOT exist empty after
any commit, so creating one requires a launch in the same command. Setting
an empty session `Ephemeral` deletes it.

`SessionDelete` SHALL refuse with `NotEmpty` while the session has
members. Creating a session SHALL NOT launch anything unless the same
command carries a launch.

### 3.2 Exit policy

A resource's `on_exit` is `Remove` or `Retain`. When an activation of a
`Remove` resource ends, the resource is removed in the same transaction
that records the end. A `Retain` resource stays with its outcome. A server
SHALL NOT start a new activation implicitly, on exit or at startup.

### 3.3 Startup reconciliation

On startup the server SHALL reconcile every activation recorded
`Starting`, `Running`, or `Stopping` under an earlier instance: one
vouched for by a live-upgrade handover is rebound; one whose recorded
process identity still matches a live process on the same boot becomes
`Lost`; any other becomes `Completed` with outcome `Unobserved`.
Reconciliation never relaunches and never claims a new process is the old
one.

## 4. The Inbox

The authority designates one session as its Inbox. It SHALL be
`Persistent`, and while designated it SHALL refuse delete and the switch
to `Ephemeral`. Its name is a label like any other.

A create that names no session places the resource in the Inbox, subject
to the caller's grants. A migration preserves imported sessions with their
members and arrangements and sets `awaiting_organization` on them; only
resources with no group go into the Inbox session. `InboxResolve` clears
the mark and changes nothing else.

The Inbox view is a client projection over Inbox sessions and marked
sessions across the authorities a client is connected to. It is not a
session that spans servers.

## 5. Operations

### 5.1 Command set

| Command | Effect |
|---|---|
| `GetOrganization` | A bounded page of authorized records, revisions, handles, and counts, with a snapshot revision and journal cursor. |
| `SessionCreate` | A session, plus a resource and its launch when one is given, in one transaction. |
| `SessionRename`, `ResourceRename` | Label only. |
| `SessionSetLifetime` | Switch lifetime (§3.1). |
| `SessionDelete` | Delete an empty session. |
| `ResourceCreate` | A resource, its membership, and its launch in one transaction. |
| `ResourceMove` | Move one resource between sessions on this authority. |
| `ResourceMoveMany` | Move a fixed, bounded set of resources to one session atomically; one refused target refuses the batch. |
| `InboxResolve` | Clear `awaiting_organization` (§4). |
| `OrganizationUndo` | Apply a receipt's inverse (§5.6). |
| `ResourceTerminate` | Ask the resource's executor to end its current activation, gracefully or by force. Answers `Accepted`; events report the outcome. |
| `ResourceRemove` | Remove a resource whose execution is proven inactive, leaving a tombstone. |
| `ResourceRelaunch` | Start a new activation from the resource's launch specification. |
| `ArrangementGet` | A document and its revision. |
| `ArrangementReplace` | Replace a document if its revision matches (§2.4 validation). |

Workspace commands are reserved for a later version. Each command carries
an `OperationId`, and each command that edits a record carries the
revision the caller expects. Commands that act on an execution carry the
live target the caller observed: handle, server instance, and activation.
A mismatched live target SHALL refuse with `Stale` before any effect.

### 5.2 Operation ids and retries

The server keeps a receipt per `OperationId` for at least 24 hours or
10,000 receipts, whichever bound is reached first. A repeat with the same
id and an identical payload SHALL return the original result without
repeating effects. The same id with a different payload SHALL refuse with
`DuplicateOperation`. The duplicate check runs before revision and
staleness checks, and authorization is re-checked before a stored result
is returned. A client that loses a reply retries with the same id; past
the receipt horizon it reconciles from `GetOrganization` and reports the
outcome as unknown.

### 5.3 Revisions

An edit whose expected revision differs from the record's current revision
SHALL refuse with `Conflict` carrying the current revision. A move checks
both sessions' revisions.

### 5.4 Results and refusals

An organization command answers `Ok` (with value, revision, and operation
id), `Accepted` (effects follow as events), or `Refused` with one of:
`Unauthorized`, `NotFound`, `Conflict`, `Stale`, `NotEmpty`,
`Unsupported`, `InvalidArgument`, `NameTaken`, `ExecutionUncertain`,
`LeaseHeld`, or `DuplicateOperation`. A server SHALL send `Accepted` and
`Refused` only in reply to organization commands. A refused command
changes nothing. A transport timeout is not a result.

### 5.5 Events

Each committed change is journaled as an organization event stamped with
its actor and operation id ([L1.md](./L1.md) §7.3): session created,
renamed, deleted, or intake-changed; membership changed; resource created
or removed; activation changed; arrangement changed; and lease changed.
Order is per authority only. A journal gap means the client refetches
`GetOrganization`.

### 5.6 Undo

A receipt for a membership, intake, or arrangement edit records its
inverse and the revisions it produced. `OrganizationUndo` is itself an
operation with its own id. It SHALL apply only while the receipt exists,
the affected records still carry the recorded revisions, and the caller
holds the original operation's grants now. It never reverses execution.

### 5.7 Killing a session

Killing a session is a client workflow, not a command: read the members
and their live targets, `ResourceTerminate` each, `ResourceRemove` each
once inactive, then `SessionDelete` with the revision read at the start.
A resource added meanwhile survives and the delete refuses with
`NotEmpty`. Clients report one result per target.

## 6. Compatibility

A client that does not see `ORGANIZATION` SHALL treat organization as
read-only and use the legacy keys of [L3.md](./L3.md) §3, which a server
that advertises the feature translates into the commands above.

Legacy `GET_STATE` and `ATTACHED` snapshots keep `SessionSnapshot.windows`:
each non-empty session reports exactly one window, with a wire id stable
for that session across calls and across a live upgrade. A session's
keep-empty facet reports `lifetime == Persistent`. `ResourceInfo` carries
its session handle in its extension block ([L1.md](./L1.md) §9.1), so a
client can join resource to session without a window.

## 7. GroupId

A `GROUP` scope selector names a session by its wire handle. It resolves
by current membership and is re-evaluated in the same transaction as a
move, so a resource moved out of a session leaves that selector at once
([workload-auth.md](./workload-auth.md) §5). The metadata
`Scope::Group` key ([L3.md](./L3.md) §2) stays an opaque grouping key with
no lifecycle.
